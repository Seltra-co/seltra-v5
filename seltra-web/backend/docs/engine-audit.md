# Seltra Engine audit

Audit date: 2026-11-01. Scope read for this implementation: core entry points, web/dev env loading, agent registry and tool dispatcher, engine URL and all direct engine callers, model-client adapter, image-generation service, diagnostics tool, cloud-sandbox adapter, and relevant schemas. This is a path-based architecture audit; it does not treat every unrelated file in the large core tree as an engine dependency.

## Architecture map

- **Desktop entry:** `core/src/main.ts` (Electron main) loads dotenv, registers typed IPC handlers through `core/src/ipc/ipc_host.ts`, and exposes IPC through the preload/client contracts under `core/src/ipc`. Renderer code uses the typed clients; privileged filesystem, settings, database, model, app-process, and tool work runs in main.
- **Web entry:** `core/scripts/web/dev.mjs` reads `.env.web` using `dotenv`, validates required web settings, then starts the Vite renderer and `core/server`. `core/server/src/main.ts` is the web gateway; its config is parsed in `core/server/src/config.ts`. Existing process variables take precedence over values loaded from `.env.web`; `.env.web` is gitignored. Hosted workspace runtimes receive a decrypted, tenant-scoped Engine key from authenticated backend entitlement/ticket responses; platform-level Engine keys are removed from each runtime's inherited environment.
- **Backend entry:** NestJS `backend/src/main.ts` loads `.env` through `ConfigModule`, applies common CORS/body/security policy, and serves `/api/v5` plus the excluded `/v1` Seltra Engine API on the same `PORT` (`SELTRA_ENGINE_PORT` must match). Tenant Engine keys are hashed for lookup and AES-GCM encrypted for runtime delivery; configure `ENGINE_KEY_ENCRYPTION_SECRET` separately from `SELTRA_ENGINE_API_KEY_HASH_SALT`. After applying the migration, `npm run engine:key:backfill` provisions keys for existing owned workspaces. Prisma uses the existing Postgres DB and migrations.
- **Agent/tools:** `core/src/pro/main/ipc/handlers/local_agent/tool_definitions.ts` is the registry; `buildAgentToolSet` applies plan/mode/consent/feature gates and binds handlers in `local_agent_handler.ts`. Results return through AI SDK tool-result messages and the app's chat stream. `generate_image` is exposed only with an engine URL and key. `repair_app` is registered for normal agent turns; it collects preview/browser/log evidence and asks the model for a diagnosis, after which the agent applies edits with normal file tools.
- **Model calls:** direct provider connections stay on their provider transport. Auto/engine connections from `get_model_client.ts` use the Seltra Engine OpenAI-compatible base URL. Local agent tool calls use `engineFetch`. In web mode the separate core gateway at port 8080 also has model/image handlers at `/v1/chat/completions` and `/images/generations`; workspace model tokens are verified there. The new backend Engine at port 3001 is the explicit engine URL configured for local web mode.
- **Generated apps and diagnostics:** app files live under the app workspace and run through the app runtime/process manager or cloud sandbox provider. `repair_app.ts` selects the running app URL, captures console errors, page errors, failed requests, HTTP failures, and a 1440x900 screenshot using Playwright; recent app warnings/errors come from the log store. Browser evidence and logs are sent to the vision model. Build/typecheck/test tools capture their own command output.

## Verified engine contract inventory

All `engineFetch` calls send JSON by default, `Authorization: Bearer <key>`, and `X-Request-ID` (legacy `X-Dyad-Request-Id` is accepted by the backend). Requests are bounded by the caller's abort signal and a 300,000 ms default timeout; repair vision overrides to 90,000 ms. The app image service uses a 120,000 ms timeout. Client errors generally read the response body as text; image clients map 401/403 to auth, 429 to rate limited, and other statuses to external errors. No client-side retry is configured in these paths.

### Auth, request IDs, errors, timeout and metering

- Seltra key format is `sk_seltra_` followed by 32 random bytes encoded base64url. Backend stores HMAC-like salted SHA-256 digests (key never stored in plaintext), iterates active hashes with `timingSafeEqual`, updates `lastUsedAt`, and checks revocation on each request. Missing/malformed/unknown/revoked keys all return 401 with `{error:{code:"invalid_api_key",message:"A valid Seltra Engine API key is required."}}`.
- A caller `X-Request-ID` is validated (1..128 safe characters) and echoed; legacy `X-Dyad-Request-Id` is accepted only for migration. Every response gets `X-Request-ID`, including parser errors via early middleware. Structured request, upstream, rejection, rate-limit, and usage logs contain request/key/workspace ids but no bearer or provider key. Upstream errors are truncated to 300 chars in logs and provider secrets/internal URLs are excluded from returned errors.
- 400 is used for invalid prompt/body input; 401 for invalid engine key; 402 `{error:{code:"insufficient_credits",...}}` for a depleted workspace balance; 429 includes `Retry-After`; 502 for upstream/invalid response; 504 for provider timeout; 503 for configuration gaps; 413 is provided by the body parser. Legacy unsupported endpoints return an authenticated 501 with endpoint name.
- Core uses abort signals and timeouts noted above. Engine upstream calls have configurable 60,000 ms default timeout and no retries; no non-idempotent call is retried. The body limit defaults to 20 MB, image input count to 4, prompt length to 2048, and rate limit to 60/minute per key and IP (process-local counter).
- Image/chat calls reserve credits before provider work, then settle actual token/image cost in a transaction; failures release the reservation. Append-only reserve, release, and usage ledger rows accompany `SeltraEngineUsage`; generated image metadata is stored in `SeltraEngineAsset`. Upstream bodies have a configurable byte cap (`SELTRA_ENGINE_MAX_UPSTREAM_MB`). Image storage uses Cloudinary when configured and local filesystem storage for development.

## Backend and scope decisions

The backend uses NestJS 10, Prisma/Postgres migrations, Jest/ts-jest, existing `WorkspaceCredit`/`CreditLedger`, existing `ProjectAsset` (not used for engine-specific metadata), Cloudinary upload helper, and Node `fetch`. No new framework/runtime was introduced. The engine module is mounted in the existing backend process and shares its port.

- **P0:** image generation, repair vision, key auth, health, request IDs, body/rate limits, structured logs, credit/usage accounting: implemented. The two tools are explicitly admitted in the core Build tool profile; image generation may run with a free chat model when the Seltra Engine key is configured. Cloudflare image model IDs must preserve slash separators in `/ai/run/@cf/vendor/model` URLs.
- **P1:** OpenAI chat completions/model listing are implemented through Cloudflare Workers AI. Search/crawl/code-search/audio/transcription/sandbox lifecycle and alternate OpenAI response/Anthropic endpoints return explicit authenticated 501 errors.
- **P2/Never:** vendor account/billing/telemetry/free-quota/legacy usage receipts are not recreated. Seltra's own WorkspaceCredit ledger is used for new Engine calls.
- Cloudflare Workers AI is the first provider. Current official REST docs use `POST /client/v4/accounts/{account_id}/ai/run/{model}` with Bearer auth; FLUX image responses expose base64 `result.image`; OpenAI-compatible chat is available at the account AI REST endpoint. Sources: [Workers AI REST API](https://developers.cloudflare.com/workers-ai/get-started/rest-api/), [FLUX.1 schnell model](https://developers.cloudflare.com/workers-ai/models/flux-1-schnell/), [Cloudflare AI Gateway REST API](https://developers.cloudflare.com/ai-gateway/usage/rest-api/). The service reads model IDs from `AI_MODEL_*` and account credentials from environment only.

## Dyad-to-Seltra rename plan

1. Runtime URL resolver has been renamed to `seltra_engine_url.ts`; `SELTRA_ENGINE_URL` and `SELTRA_ENGINE_API_KEY` take precedence. There is no hosted default URL. `DYAD_ENGINE_URL` and the persisted `providerSettings.auto.apiKey` are read only when Seltra settings are absent, with one-time deprecation warning.
2. Existing persisted auto-provider key is migrated into encrypted `seltraEngineApiKey` only when it already has the Seltra `sk_seltra_` format. A third-party Dyad-issued key cannot be silently converted to a Seltra key because Seltra hashes/owns its issued-key registry; that key remains a legacy fallback only when the legacy URL is explicitly configured.
3. Engine URL and key transport names and user-facing engine errors/logs use Seltra names. Existing upstream Dyad adapter types, XML tags, attribution, package/license material, and unrelated product settings are not blindly renamed.
4. `core/scripts/web/check-seltra-engine-url.mjs` scans production runtime source and fails on a hardcoded legacy engine host.
